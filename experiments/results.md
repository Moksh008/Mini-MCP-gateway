## Reading the results

* **Fixed cost:** full discovery resends every definition on every model call, so it grows linearly with the catalog. Incremental discovery's fixed cost is constant (3 meta-tools).
* **Variable cost:** incremental pays per tool *used* (one search + one schema fetch), plus extra round-trips. At 20 tools, single-tool tasks are already cheaper but multi-tool tasks can cost more, because the full catalog is small; the crossover moves sharply in incremental's favour as the catalog grows (Part B) — at hundreds of tools, full discovery is impractical and at thousands it exceeds typical context windows.
* **Latency trade-off:** incremental adds 2 model round-trips per newly needed tool. Hybrid setups (pin a few hot tools, search the long tail) reduce this; the gateway supports direct calls by qualified name on `/mcp` for exactly that.
* **Prompt caching** lowers the $ cost of a static tool prefix in full mode, but not the context window it occupies or the selection-accuracy cost of showing a model thousands of tools.
* **Search quality** is the real risk of incremental discovery. Half of the synthetic distractors reuse the real tools' vocabulary (ride, fare, order, invoice…), so top-1 accuracy drops as they are added while top-5 holds — which is why `search_tools` returns several candidates and lets the model choose. The lexical BM25 ranker is a baseline; it is pluggable (`ToolSearchIndex.search`) for embedding/hybrid retrieval. Synthetic distractors are a proxy, not a substitute for a real catalog.
